## Why

The first version of `agentify-project` (shipped in `add-agentify-project-skill`) audits one repo, picks whichever harness it detects, and gates every write behind a confirmation prompt. Real usage — grounded in how `the reference repo` actually sets itself up, plus a round of exploration on delivery mechanics — asks for more: always scaffold **both** Claude Code and Cursor, run as a **non-interactive** staged pipeline instead of a confirm-per-change loop, deliver the whole result as **a single pull request** so the repo owner reviews and merges rather than the skill applying changes directly, do real **tool installation** (OpenSpec CLI, the `skills` CLI, repomix, the codebase-memory MCP server — framed as an **extensible registry**, not a fixed list) rather than just auditing files, use the existing `find-skills` skill to drive skill recommendations, validate and auto-fix any **custom/local skills** already in the repo against `skill-standard`, and generate real architecture documentation under `docs/` in the two-tier style the reference repo already uses. The safety model changes accordingly: since nothing pauses to ask mid-run, safety comes from two places instead — a **uniform pre-flight prerequisite gate** that stops the entire run before anything is touched if a hard requirement is missing, and **PR-based delivery**, so nothing ever lands on a real branch without human review.

## What Changes

- **BREAKING**: Replace the confirm-before-every-write safety model with delivery as a **single pull request**: the skill creates a dedicated branch, applies each pipeline stage as its own commit, pushes, and opens a PR (`gh pr create`) summarizing every stage's outcome — including manual follow-ups the owner still needs to do. Nothing is ever written directly to the branch the invoking session started on.
- **BREAKING**: Add a **uniform pre-flight prerequisite gate**, run before any branch is created or any file touched: git working tree must be clean, the `gh` CLI must be present, authenticated, and have a pushable remote, and Node/npm must be available. All three are treated as equal prerequisites — if **any** is missing, the skill stops immediately with a diagnosis of what's missing and a concrete recommended fix, and makes no changes at all.
- **BREAKING**: Replace harness *detection-then-pick-one* with *always set up both* Claude Code and Cursor by default (mirroring the reference repo's `.claude/` + `.cursor/` + `.agents/` three-way layout), unless the user's request explicitly scopes to one harness. Harness scope is fixed at exactly these two — not an open-ended N-harness system.
- Restructure the skill's process into an explicit staged pipeline, each stage its own PR commit: pre-flight → tool setup → repo/stack analysis → harness scaffolding (both) → skill wiring → permission hygiene → MCP + repomix setup → architecture docs generation → open PR.
- Add a pre-flight detection pillar (separate from the prerequisite gate above): inventory what agent scaffolding already exists (`.claude/`, `.cursor/`, `.agents/`, `openspec/`, `docs/`, repomix configs, MCP registration, detected tech stack) so every later stage merges against one accurate map instead of re-detecting per pillar.
- Add a tool-setup pillar built as an **extensible supported-tools registry** (not a fixed four): each entry declares how to detect it, how to install/configure it, whether its output is repo-committed (→ part of the PR) or machine-global (→ a local prerequisite, never a PR deliverable), and how re-running verifies it's already done. Initial entries: OpenSpec CLI, the `skills` CLI, repomix, and the codebase-memory MCP server — more can be added later as new entries without changing the pipeline's logic.
- The codebase-memory MCP server and the Serena MCP server are both set up by discovering and installing their corresponding skill via `find-skills` + the `skills` CLI (`codebase-memory-mcp-intelligence`, `setup-serena-mcp`), then following that skill's own instructions — rather than agentify-project hardcoding install/registration commands itself. Registration for both is **project-scoped only** (`.mcp.json` for Claude Code, `.cursor/mcp.json` for Cursor); global/cross-repo registration (what the reference repo itself actually uses for codebase-memory) is never applied automatically — it's documented as a manual follow-up in the PR description, since a PR can't represent a change to machine-global state. Repomix setup follows the same discover-and-install-a-skill pattern (`repomix-explorer`), replacing the earlier direct devDependency-and-config-write approach.
- Change skill wiring to use `find-skills` plus the real `skills` CLI (`npx skills add <source>@<skill> -y`) against the detected tech stack, matching how the reference repo's `.agents/skills/` + root `skills-lock.json` are actually populated, instead of the prior skill's manual "copy a folder" mechanism. Skills installed this way are trusted by construction and are not re-validated.
- Add a **custom/local skill validation and drift-enforcement** pillar: any skill already present in the repo that *isn't* tracked in `skills-lock.json` (i.e., not installed via `find-skills`/the `skills` CLI) gets checked against `skill-standard`'s validation checklist. Mechanical violations (frontmatter errors, directory-name mismatch, disallowed keys, absolute paths, description length) are fixed directly and committed as their own PR commit. Judgment-based violations (vague description, non-actionable steps) are reported in the PR description as a recommendation, never auto-rewritten.
- Add an architecture-documentation pillar: analyze the repo and generate/merge `docs/ARCHITECTURE.md` (system context, component diagram, service catalog, topology, cross-service sequences, data model, known issues — via Mermaid + tables) plus `docs/services/<name>.md` per service for multi-service repos, scaled down to a single `docs/ARCHITECTURE.md` for single-service repos.
- Generalize stack detection for polyglot, non-monorepo-tooled repos (walk top-level directories for independent manifests; don't assume a single workspace root or JS-tooling orchestration).

## Capabilities

### Modified Capabilities
- `agentify-project-skill`: The requirements below replace the confirmation-gated, single-harness, audit-only, direct-write behavior from `add-agentify-project-skill` with a staged, non-interactive, both-harness pipeline delivered as a single reviewable pull request, gated by a uniform pre-flight prerequisite check, performing real tool installation via an extensible registry, validating/auto-fixing custom skills against `skill-standard`, and generating architecture documentation.

### New Capabilities
_None — this is a substantial revision of the same capability, not a new one._

## Impact

- Affected paths: `agentify-project/SKILL.md`, all files under `agentify-project/references/`, `agentify-project/evals/evals.json` (and fixtures), and `openspec/specs/agentify-project-skill/spec.md` once synced.
- No code/runtime systems in this repo are affected — this repo only distributes skill definitions. The skill's own behavior, once installed into a *target* project, will perform real installs/config changes and open a real pull request there — those actions are out of scope for this repo's own CI/build, but the design and safety rules for them are exactly what this change specifies.
- New external dependency for running the skill: the `gh` CLI (authenticated, with a pushable remote) is now a hard prerequisite, not optional.
- Depends on: `skill-standard` (format/validation, now also used for custom-skill drift enforcement), the built-in `find-skills` skill (skill-wiring pillar, and the discovery mechanism for the MCP/repomix registry entries below), and three externally-published skills as the authoritative source for their respective install/registration instructions (not duplicated in agentify-project itself): `aradotso/mcp-skills@codebase-memory-mcp-intelligence`, `neolabhq/context-engineering-kit@setup-serena-mcp`, and `yamadashy/repomix@repomix-explorer`.
