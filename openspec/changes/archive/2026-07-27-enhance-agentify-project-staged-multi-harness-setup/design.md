## Context

`agentify-project` v1 (from `add-agentify-project-skill`) is a confirm-gated, single-harness (detected, not both) audit skill. This revision is grounded in a survey of `the reference repo`, a real repo that already does most of what's being asked for, plus a round of exploration that settled the delivery mechanism and safety model further than the initial proposal did.

**What the the reference repo survey found** (unchanged from the first draft of this design):

- **Docs**: `docs/ARCHITECTURE.md` (system context, component/container Mermaid diagrams, service catalog table, RabbitMQ topology table, cross-service sequence diagrams, shared data model `erDiagram`, known issues) plus `docs/services/README.md` (index) and one `docs/services/<name>.md` per service (Role, Tech stack & entry point, HTTP API, Data models, RabbitMQ, Known issues — citing exact `file:line`).
- **Harness scaffolding, three-way**: `.claude/` (skills, commands, `settings.local.json` — *not* `settings.json`), `.cursor/` (`rules/*.mdc` with `description`/`globs`/`alwaysApply` frontmatter, skills, commands), and `.agents/skills/` as the **canonical, CLI-managed** skill store with root `skills-lock.json` (source repo, `sourceType`, `skillPath`, `computedHash` per skill) — `.claude/skills/` and `.cursor/skills/` are the same skills mirrored per harness.
- **Agent instructions, two distinct files with different jobs**: `CLAUDE.md` is a short, stable pointer; `AGENTS.md` is a living, append-only log of learned conventions. Not near-duplicates of the same content.
- **skills CLI**: a real npm package (`"skills": "^1.5.20"` in root `package.json`), invoked via `npx skills add <owner>/<repo>@<skill> -y` / `npx skills find <name>` / `npx skills remove`.
- **repomix**: project-scoped, committed config files, consistent shape (XML output, summary/directory-structure on, compression on, gitignore-aware, security check on).
- **codebase-memory MCP**: registered at the **user/global** level, *not* committed to the project.
- **OpenSpec**: already initialized, CLI invoked directly as `openspec` (not via npx).
- **Stack**: polyglot, non-monorepo-tooled — folder-per-service, no JS workspaces, no Nx/Turborepo/pnpm-workspaces.

**What the exploration session settled on top of that** (this is the substantial delta from the first design draft):

- Delivery is **a single pull request**, not direct writes to the branch in use — the skill creates a branch, commits one stage at a time, pushes, and opens a PR via `gh pr create`.
- Pre-flight includes a **uniform prerequisite gate**: git working tree clean, `gh` present/authenticated/pushable, Node/npm present. All three are equal-weight prerequisites — any missing one stops the entire run before any side effect, with a diagnosis and a recommended fix.
- Tool setup is framed as an **extensible registry**, not a fixed set of four bespoke integrations.
- MCP registration for the codebase-memory server is **project-scoped only, always** — never automatic global/cross-repo registration, since a PR can't represent machine-global state.
- Skills already in the repo that aren't tracked in `skills-lock.json` (custom/local, not registry-installed) get validated against `skill-standard` and **mechanically drift-corrected**: structural violations are auto-fixed and committed; judgment-based ones are reported, not rewritten.

## Goals / Non-Goals

**Goals:**
- Turn `agentify-project` into a **staged pipeline delivered as one pull request**: pre-flight (prerequisite gate + detection) → tool setup → repo analysis → harness scaffolding (both, always) → skill wiring → permission hygiene → MCP/repomix setup → architecture docs → open PR. Each stage is its own commit.
- Make safety structural in two complementary ways: (1) a **uniform pre-flight prerequisite gate** that refuses to start at all if git isn't clean, `gh` isn't usable, or Node/npm is missing — with a clear diagnosis and fix recommendation, not a vague failure; (2) **PR-based delivery**, so even if a stage's content decision turns out wrong, nothing has touched a real branch until a human reviews and merges.
- Keep content-level changes merge-first (preserve hand-authored content, add what's missing) as good PR hygiene — smaller, more reviewable diffs — even though the primary safety guarantee is now "nothing lands without review," not "nothing is ever destructive."
- Always scaffold **both** Claude Code and Cursor by default — fixed at exactly these two harnesses, not an open-ended system — unless the user's request explicitly scopes to one.
- Perform **real tool installation** via an **extensible supported-tools registry**: each entry defines detect/install/scope(repo vs. machine-global)/idempotency-check. Five initial entries (OpenSpec CLI, `skills` CLI, repomix, codebase-memory MCP, Serena MCP), more addable later without touching pipeline logic. The three MCP/repomix entries are satisfied by discovering and installing their corresponding skill via `find-skills` + the `skills` CLI, not by agentify-project's own bespoke install commands.
- Use `find-skills` + the real `skills` CLI for skill wiring, replacing manual folder-copying.
- Validate and **mechanically drift-correct** custom/local skills (not registry-installed ones) against `skill-standard`, committing structural fixes and reporting judgment-based issues without rewriting them.
- Generate real **architecture documentation** under `docs/`, following the reference repo's two-tier structure, scaled to the target repo's actual shape.
- Generalize stack detection for polyglot, non-monorepo-tooled repos.

**Non-Goals:**
- Not delivering changes directly to whatever branch the invoking session is on — everything lands via one PR on a dedicated branch.
- Not treating any prerequisite as "soft" — git-clean, `gh`, and Node/npm are all equally hard gates. No degraded/partial-run mode.
- Not fabricating or hardcoding exact CLI flags/install commands for the codebase-memory MCP server, the Serena MCP server, or repomix, since each surface might drift independently — each is set up by discovering and installing its corresponding skill (`codebase-memory-mcp-intelligence`, `setup-serena-mcp`, `repomix-explorer`) via `find-skills` + the `skills` CLI and following that skill's own instructions, instead of agentify-project duplicating install commands itself.
- Not performing genuinely global/system-wide *deliverables* — project-scoped config only for anything that would otherwise need to go in the PR; global/cross-repo alternatives are documented, never auto-applied.
- Not auto-rewriting a skill's judgment-based content (description quality, step actionability) to satisfy `skill-standard`'s subjective checklist items — only mechanical/structural violations are auto-fixed.
- Not inventing a permission-hygiene mechanism for harnesses without one (still Cursor, as of this writing).
- Not assuming every target repo is a monorepo or polyglot like the reference repo — the pipeline and stack analysis must degrade gracefully to a small single-service repo.

## Decisions

1. **Safety is structural, from two independent mechanisms, not from asking.** (a) A uniform pre-flight prerequisite gate stops the whole run before anything happens if a hard requirement is missing. (b) Delivery as a single PR means nothing lands on a real branch without human review — see Decision 2. Content-level merge-first behavior (Decision 3) is still good practice for producing a reviewable diff, but it is no longer the *primary* safety guarantee the way it was in the first draft of this design; the PR gate is.

2. **Delivery is one pull request per run: dedicated branch, one commit per stage, push, `gh pr create`.** The skill creates a branch (e.g. `agentify/<date>-setup`), applies each pipeline stage as its own commit (tool setup, harness scaffolding, skill wiring, permission hygiene, MCP/repomix setup, architecture docs), pushes it, and opens a PR whose description summarizes every stage's outcome — including anything that needs a manual follow-up (like global MCP registration). Rationale: this turns "non-interactive" from a risk into a non-issue — the owner reviews and merges (or doesn't) exactly like any other PR, and the staged-commit history *is* the stage list, which makes review far easier than one giant diff. Alternative considered — write directly to the current branch with a dry-run/preview mode on first use — rejected in favor of PR review, which doesn't require remembering to use a special mode and works the same way every time.

   **Re-run detection mechanism (resolved):** before creating a branch, the skill checks for a prior run's still-open PR by combining the branch-naming convention (`agentify/<year>-<month>-setup`) with `gh pr list --head <branch-name> --state open --json number,url`. If found, it pushes new commits onto that branch/PR instead of creating a second one — this is what the "Idempotent re-runs" requirement in the spec commits to, and what the branch-naming-plus-`gh pr list` combination in the implementation performs.

3. **Content-level changes still merge, not clobber, wherever they land in the PR.** Every write is computed as a merge against existing content (preserving hand-authored material, adding what's missing or demonstrably stale). Destructive/replace-wholesale behavior for a specific file only happens when the user's own request explicitly asks for it. Rationale: even though the PR gate is now the primary safety net, a PR full of wholesale replacements is much harder to review than one of targeted merges — this is about producing a *good* PR, not just a *safe* one.

4. **Uniform pre-flight prerequisite gate: git-clean, `gh`-usable, Node/npm-present — all equal, all hard-stop.** Before creating a branch or touching any file, the skill checks: the working tree is clean (nothing stashed or committed on the caller's behalf), the `gh` CLI is present, authenticated, and the repo has a pushable remote, and Node/npm is available (needed for every `npx`-based tool). If any check fails, the skill stops immediately, makes no changes, and reports which check(s) failed with a concrete recommended fix (e.g. "working tree has uncommitted changes — commit or stash them, then re-run"; "`gh` not authenticated — run `gh auth login`"; "Node.js not found — install from nodejs.org or your package manager"). Rationale: all three are prerequisites for the same thing — producing a valid PR — so there's no principled reason to treat one as softer than another; a uniform policy is simpler to implement and simpler to explain than a tiered one.

5. **Both harnesses, always, fixed at exactly two.** The staged pipeline scaffolds Claude Code and Cursor unconditionally, regardless of which harness-specific directories currently exist, unless the user's request explicitly scopes to one. This is a closed set of two, not an open-ended N-harness system — adding a third harness later would be a deliberate future revision, not something the pipeline auto-discovers. Rationale: matches the reference repo's own three-way layout and the user's explicit confirmation that scope is fixed at these two.

6. **Agent instructions: `CLAUDE.md` and `AGENTS.md` are not forced into lockstep duplication.** Per the the reference repo precedent, `CLAUDE.md` may stay a short, stable pointer while `AGENTS.md` (and, where relevant, Cursor rules) carry the fuller, evolving detail. For a small/new repo without such a split yet, the default draft is one reasonably-sized content set applied consistently; the split is offered as the repo grows, not forced upfront.

7. **Tool setup is an extensible supported-tools registry, not five bespoke integrations.** Each entry declares: `detect` (how to check it's already set up), `install` (how to set it up if missing), `scope` (`repo` — output is a committed file, goes in the PR — or `machine-global` — a local prerequisite for running the pipeline, never a PR deliverable), and an idempotency check. Initial entries:
   - **OpenSpec CLI** — `detect`: `openspec --version` succeeds; `install`: `npm install -g openspec`; `scope`: machine-global (the CLI itself) producing a `scope: repo` deliverable (`openspec init`'s output), run only if `openspec/` doesn't already exist.
   - **`skills` CLI** — `detect`: `npx skills` resolves; `install`: add `skills` as a devDependency when the target is a Node project (matching the reference repo's own `package.json`); `scope`: repo (the devDependency entry) with the CLI itself invoked via `npx` rather than installed globally.
   - **repomix** — `detect`: a `repomix.config.json` (or equivalent) exists, or the `repomix-explorer` skill is already installed under `.agents/skills/`; `install`: discover the repomix skill via `find-skills` and install it (`npx skills add yamadashy/repomix@repomix-explorer -y`) if not already present, then follow that skill's own instructions for setting repomix up in this repo; `scope`: repo (the skill's presence in `.agents/skills/` + `skills-lock.json`, plus whatever config file its instructions produce).
   - **codebase-memory MCP** — `detect`: a matching entry in project-scoped `.mcp.json`/`.cursor/mcp.json`, or the `codebase-memory-mcp-intelligence` skill is already installed; `install`: discover the codebase-memory MCP skill via `find-skills` and install it (`npx skills add aradotso/mcp-skills@codebase-memory-mcp-intelligence -y`) if not already present, then follow that skill's own instructions to register the MCP server, project-scoped only; `scope`: repo, project-only — never global (see Decision 8).
   - **Serena MCP** — `detect`: a matching Serena entry in project-scoped `.mcp.json`/`.cursor/mcp.json`, or the `setup-serena-mcp` skill is already installed; `install`: discover the Serena MCP setup skill via `find-skills` and install it (`npx skills add neolabhq/context-engineering-kit@setup-serena-mcp -y`) if not already present, then follow that skill's own instructions to register the MCP server, project-scoped only; `scope`: repo, project-only — never global (see Decision 8).

   Adding a sixth tool later (a linter, Playwright, whatever) means adding one more entry in this same shape — the pipeline's tool-setup stage iterates the registry generically rather than having bespoke per-tool logic. Rationale: this is exactly what "I could add more later" requires structurally — a fixed implementation would need a redesign for the next tool; a registry doesn't. The repomix, codebase-memory MCP, and Serena MCP entries additionally share a sub-pattern — "detect/install via `find-skills` + the `skills` CLI, then defer to that skill's own instructions" — rather than each maintaining its own copy of install commands that could drift from the real tools' CLI surfaces.

8. **MCP registration for the codebase-memory server and the Serena MCP server is project-scoped only, always — never automatic global/cross-repo.** This strengthens the first draft's "prefer project-scoped" into "only ever project-scoped, automatically," for both MCP servers the registry supports. Rationale: a PR can only represent repo-committed changes; a global/user-home registration (what the reference repo itself actually does for codebase-memory, for cross-repo indexing convenience) can't be reviewed or merged as part of a PR, so the skill never performs it automatically for either server. When cross-repo indexing is what the user actually wants, the PR description documents the manual global-registration steps (read from the same installed skill used for the project-scoped install) as a follow-up, rather than the skill silently modifying machine-global state that the PR review process can't see.

9. **Custom/local skill validation and drift enforcement, scoped to non-registry skills only.** During pre-flight's inventory of `.claude/skills/`, `.cursor/skills/`, `.agents/skills/`, each existing skill is classified as registry-sourced (present in `skills-lock.json`) or custom/local (not in the lockfile). Registry-sourced skills are trusted by construction and are never re-validated. Custom/local skills are checked against `skill-standard`'s validation checklist, and violations are split by kind:
   - **Mechanical** (frontmatter field errors, directory-name ≠ `name`, disallowed top-level keys, absolute paths, description length) — fixed directly and committed as their own PR commit.
   - **Judgment-based** (vague description, non-actionable steps) — reported in the PR description as a recommendation; never auto-rewritten.

   Rationale: mechanical fixes are deterministic and safe to apply without asking — they don't change what a skill *means*, only whether it's correctly formed. Rewriting a skill's actual content to satisfy a subjective checklist item risks changing intent the skill's original author had, which is exactly the kind of judgment call that shouldn't happen silently even under a PR-review safety net (a rewritten description is a much harder thing for a reviewer to sanity-check than a frontmatter fix).

10. **Skill wiring via `find-skills` + the real `skills` CLI, replacing manual copying.** The stage: (a) run the stack analysis, (b) invoke `find-skills` with the detected stack as the query, (c) for each relevant match not already installed, run `npx skills add <source>@<skill> -y`, relying on the CLI's own management of `.agents/skills/`, per-harness mirrors, and `skills-lock.json`. Because delivery is a PR, non-interactive `-y` usage is just the pipeline's normal invocation, not a special "skip confirmation" case.

11. **Architecture docs pillar mirrors the reference repo's structure, scaled to repo shape.** Always generate/merge `docs/ARCHITECTURE.md` (system context, component/container diagram, service catalog, topology table for any message broker present, cross-service sequence diagrams, shared data model, known issues) grounded strictly in what the stack analysis actually finds. Multi-service repos additionally get `docs/services/README.md` + one `docs/services/<name>.md` per component; single-service repos get only `ARCHITECTURE.md`.

12. **Stack detection generalized for polyglot, non-monorepo-tooled repos.** Detection walks top-level directories for independent manifests rather than assuming a single workspace root or JS monorepo tooling; it also reads each component's CI workflow files to determine actual per-component test coverage.

13. **Pre-flight builds one shared "what's already here" map, used by every later stage — separate from, and after, the prerequisite gate.** The prerequisite gate (Decision 4) runs first and can stop the whole run; only once it passes does pre-flight build the detection map (existing instructions files, `.claude`/`.cursor`/`.agents` contents plus skill lockfile classification, `openspec/`, `docs/`, repomix configs, MCP registration, detected stack) that every subsequent stage reads from.

## Risks / Trade-offs

- [`gh` CLI as a hard prerequisite excludes environments that use a different git host or no PR workflow at all] → Documented as a known limitation, not silently worked around; the pre-flight failure message says exactly why and what to install/configure. A non-GitHub delivery mechanism is out of scope for this revision.
- [PR-based delivery means results aren't visible until CI/review catches up, unlike the old direct-write model] → This is the intended trade-off — the whole point was moving the safety net from "hope the merge logic was right" to "a human reviews before it's real." Not treated as a downside to engineer around.
- [Auto-fixing custom skills' mechanical violations could still surprise an owner who deviated from the standard deliberately] → The fix lands as its own clearly-labeled commit in the PR, independently reviewable and revertable without touching anything else the run did.
- [Installing real tools (global CLI installs, npm devDependencies) still has meaningful blast radius even with PR delivery, since some actions — like installing the `openspec` CLI globally — happen on the machine running the pipeline, not just in the repo] → Scoped as narrowly as each tool allows (Decision 7's `scope` field) and gated by the same uniform prerequisite check for anything the pipeline depends on to run at all.
- [Hardcoding the codebase-memory MCP server's, Serena MCP server's, or repomix's exact install commands risks drifting from the real tools' CLI surfaces] → Resolved by discovering and installing each tool's corresponding skill (`codebase-memory-mcp-intelligence`, `setup-serena-mcp`, `repomix-explorer`) via `find-skills` + the `skills` CLI and following that skill's own instructions (Decision 7), instead of duplicating install commands in agentify-project itself.
- [No verified `repomix` skill actually authors a `repomix.config.json` — the chosen `repomix-explorer` skill (highest-installed, from repomix's own maintainer org) is framed around running repomix and reading its packed output, not around writing a config file] → Accepted trade-off: the repomix registry entry's guarantee narrows from "a config file will exist after this stage" to "the `repomix-explorer` skill will be installed and its own instructions followed" — whether a config file results depends on that skill's actual content, not on agentify-project's own logic. Documented explicitly rather than silently assumed equivalent to a bespoke config-writer.
- [Always scaffolding both harnesses may set up one the user doesn't use] → Lower-cost now than in the first draft, since nothing is real until the PR is merged — the owner can simply decline to merge the parts they don't want, or ask for a revision.
- [Architecture-doc generation could produce a stale or wrong picture if the repo is unusual/large] → Grounded strictly in what stack detection actually finds (Decision 11/12) — no invented services, endpoints, or data models.
- [`find-skills` + `skills` CLI wiring, and some tool installs, depend on network access] → Pre-flight's uniform gate doesn't currently check network reachability explicitly; a network failure mid-pipeline should be reported plainly in the PR description as an incomplete stage, not silently skipped (see Open Questions).
- [Re-running against a repo that already has an open agentify PR from a prior run] → Idempotency requires detecting an existing open PR/branch from a prior run and pushing additional commits to it rather than opening a duplicate PR.

## Migration Plan

Purely a revision of one existing skill's content (`agentify-project/`) plus its synced main spec — no other skills or repo systems are touched. Rollback is reverting the skill's files to the `add-agentify-project-skill` archived version if the new behavior proves wrong in practice; no data migration involved since this repo only distributes skill definitions.

## Open Questions

- Should a network failure *mid-pipeline* (e.g. `find-skills`/`skills` CLI can't reach the registry after the uniform pre-flight gate already passed) abort the whole run, or should it complete the PR with that one stage marked incomplete and explained? Leaning toward the latter (consistent with "always report, never fail silently"), but not fully settled — neither the spec nor the implementation currently commits to either behavior.
